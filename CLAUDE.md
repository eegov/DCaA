# DCaA: учёт студентов

## Что за проект
Лабораторные по курсу «Распределённые вычисления и приложения», вариант 2 (учёт студентов).
Требования преподавателя: `docs/labs-requirements.md`. Лабы 1–7 развивают одну систему.
Как устроена обвязка и почему: `docs/harness.md`.

## Инварианты
- Поведение меняется только через OpenSpec: propose → apply → ревью → archive.
  Причина: преподаватель сверяет код со спецификацией, код без спеки считается самодеятельностью.
  Правки без изменения поведения (сборка, документация, исправления по ревью) записываются задачей
  в `tasks.md` активного изменения, без правки спецификаций.
- Делаем только текущую лабу. Отчёты, шлюз, очередь, JWT появятся в лабах 2–7.
  Причина: код без требования придётся объяснять на сдаче и тащить через все следующие лабы (overengineering).
- Схема БД меняется только новым changeset Liquibase, `ddl-auto` остаётся `validate`.
  Причина: Liquibase хранит checksum применённых changeset и не даст запустить приложение после их правки.
- Не усложняй: никаких защитных проверок «на всякий случай» и абстракций под будущие лабы.
  Каждая ветка кода должна соответствовать сценарию в спецификации.

## Ловушки
- `.env` читают и Compose, и Spring Boot (`spring.config.import`). Внутри Docker-сети сервис ходит в БД по `db:5432`,
  поэтому `DB_HOST` и `DB_PORT` для контейнера задаются в `compose.yaml`, а не в `.env`.
- На машине разработчика порт 5432 занят службой Windows PostgreSQL 18 (режим без Docker), поэтому Docker-база
  публикуется на 55432 через `DB_PORT` в `.env`. Чужие процессы и службы не останавливаем.
- Интеграционные тесты используют Testcontainers: без запущенного Docker `verify` падает, тесты тут ни при чём.
- Основная ОС разработчика Windows: в документации команды сначала для PowerShell (`.\mvnw.cmd`).

## Как проверить
- `./mvnw verify`: сборка, интеграционные тесты, проверка миграций на чистой БД.
- Фича готова только после скилла `code-review`.

## Git
master ← dev ← `feature/*`, `fix/*`, `chore/*`. Коммиты в формате Conventional Commits, в dev вливаем через `git merge --no-ff`.
- dev: всё, что сделано до сдачи. При сдаче на dev ставится аннотированный тег `labN`, преподаватель получает ссылку на тег.
- master: только лабы, принятые преподавателем. После приёмки: `git switch master`, `git merge --no-ff labN`.
  Причина: master служит отметкой «принято», а тег хранит сданную версию, когда dev уже ушёл к следующей лабе.
- Тег и вливание в master только по прямой просьбе пользователя: о приёмке знает только он.
Нарушения ловят хуки из `.githooks/`: при отказе прочитай сообщение хука и исправь причину, а не обходи проверку.
